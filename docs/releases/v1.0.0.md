# rote v1.0.0

Historical note: the source tag is retained, but the macOS source-test gate stopped its release workflow before binary assets were published. These are the original release notes; use the [v1.0.1 notes](v1.0.1.md) for the replacement release and current installation version. The v1.0.0 tag itself is unchanged.

The first stable release of **a cron that remembers what it did**: scheduled jobs, persistent run history, captured output, and a live terminal dashboard.

## Highlights since v0.2.1

- Optional per-job `history_limit`: atomically record a run and retain the newest N records. Omitted or `0` still means unlimited history.
- One scheduler per database, enforced with an OS lock. A read-only dashboard, history queries, and manual runs remain available while the scheduler runs.
- Two-stage shutdown: the first Ctrl+C/SIGTERM stops scheduling and waits for active work; a second signal cancels jobs/hooks and persists their results.
- Correct failure exit codes for runner errors, output-capture failures, and signal termination. Negative timeout values are rejected before execution.
- Faster latest/history queries that avoid loading historical output blobs; output is fetched only when requested.
- Cancellable in-process write queues shared by handles for the same database.
- Dashboard read failures are visible and retried; recovered errors clear, and switching jobs cannot display another job's stale history.
- Refreshed demo and reproducible, isolated recording script.

## Upgrade notes

1. Stop every scheduler and manual writer and allow graceful shutdown to finish. Close dashboards, then back up the configuration and database. Never delete a scheduler's `.lock` file while it is running.
2. Install the archive/package matching your operating system and architecture, or use the install script/Homebrew instructions in the README.
3. Check `rote version` reports `rote 1.0.0`, then restart one scheduler.

The database schema is unchanged from v0.2.1. Existing valid configurations continue to work without adding `history_limit`; upgrading alone never prunes history. Enabling or lowering a positive history limit can permanently delete old records and output on subsequent writes. A rollback cannot restore deleted history without a backup.

Behavior changes to account for in scripts and services:

- A second scheduler using the same database now exits with an error. Use `rote tui` to observe the existing scheduler.
- `rote run` reports runner errors or signal termination with exit code `126`, and timeouts with `124`; ordinary command exit codes are propagated.
- The first shutdown signal waits for active jobs/hooks. Send a second signal if cancellation is required; forced scheduler exits use `130`/`143`.
- Negative timeouts are invalid rather than silently acting as no timeout.

Before downgrading to v0.2.1, stop v1.0.0 completely and remove `history_limit` from the configuration (v0.2.1 rejects unknown fields). Do not run old and new schedulers concurrently: the old release does not honor the new scheduler lock.

## Compatibility and distribution

The documented CLI, configuration fields, exit-code meanings, and existing history readability are stable within 1.x. Human-readable table/TUI formatting and direct SQL access to the internal database schema are outside that contract.

Archives are provided for Linux and macOS on amd64 and arm64, with Linux deb/rpm/apk packages and SHA-256 checksums. macOS binaries are not Developer ID signed or notarized. The Homebrew cask removes the download quarantine attribute; this is not a claim of Apple notarization.

The release workflow tests source on all four platforms before publishing. After publication it downloads and verifies the actual archives, reruns process tests (including Linux pseudo-terminal tests), checks upgrades from v0.2.1, and tests installation paths. Consult the workflow result for this tag for the actual verification outcome; the existence of a release alone is not evidence that every post-publication check passed.
